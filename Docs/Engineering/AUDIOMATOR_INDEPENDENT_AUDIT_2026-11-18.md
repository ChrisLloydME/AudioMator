# AudioMator independent engineering audit

**18 November 2026 · main · `b37de1133ab7b36fa5e0a3073bec18e3384cfd70`**

> **Dated evidence.** This report records the 18 November 2026 audit of the exact working tree identified above. Source line numbers refer to that baseline. The [supporting record](AUDIOMATOR_INDEPENDENT_AUDIT_EVIDENCE_2026-11-18.md) retains the evidence and reproduction inputs for independent review.

## Executive assessment

**Hold a general production release of this working tree.** AudioMator builds successfully and its existing tests provide substantial evidence for ordinary metadata edits, format mapping, and controlled failure paths. The audit nevertheless found two ways to overwrite or delete metadata beyond the intent represented in an import preview. It also found gaps in rename recovery and revision handling, and a lyrics workflow that can apply a result to a newer file than the one used for matching. These affect the product’s primary role as an editor of existing user data.

The strongest parts of the implementation are the explicit metadata adapter boundary, versioned commits, path reservations that order overlapping mutations, and a test matrix that checks actual persisted data across many fields. The central weakness is the gap between those transactional primitives and the workflow that chooses a file, presents an intent, handles cancellation, and publishes the resulting state. Different tools bind these steps to different versions of the file or session. Passing the shared transaction layer does not establish that a tool wrote the right intent to the right file.

The baseline passed **13 evidence-policy tests, 62 Foundation tests, and 630 app-hosted XCTest cases**, with all expected names present and no skips or expected failures. An unsigned Release build passed the repository’s minimum-OS artifact check and contained arm64 and x86_64 slices in the app and bundled framework. An independent FLAC test failed on the untouched production implementation in the temporary copy: the preview identified only Track Number for removal, and the readback showed both Track Number and Total Tracks absent. The signed and notarized distribution artifact, supported-OS runtime behavior, and interactive acceptance remain unverified.

#### AM-04 · Process interruption can strand audio files under hidden staging names

**Confirmed crash-recovery deficiency · High confidence · Reproduced with the production transaction function.** Batch rename moves sources to random hidden staging names before moving them to their final locations. Startup has no staging reconciliation and normal enumeration skips hidden files. ## Architectural assessment

The SwiftUI and AppKit front end sends edits through a MainActor application model. The app owns selection in `AudioViewModel`, stores separate Quick Import and watched-folder collections, and publishes the visible selection and Inspector draft from those sources. Feature stores own specialist sessions. Domain helpers implement templates, matching policy, track numbering, and capability-aware intent. The app delegates container-specific reads and commits to its TagLib adapter and uses AVFoundation for selected read fallbacks. The adapter translates app fields and package results and reports durability uncertainty. This boundary allows real package conformance tests and isolated app workflow tests. The shared file transaction executor validates expected state, deliberately completes a started synchronous write, and gives readback its own timeout. The path reservation actor acquires multi-file keys together and distinguishes queued cancellation from a started commit. Those mechanisms should be retained. [Application composition (line 21)](../../AudioMator/App/AudioMatorApp.swift) · [Selection and source ownership (line 109)](../../AudioMator/Features/Main/ViewModels/AudioViewModel.swift) · [Read projection (line 1)](../../AudioMator/Infrastructure/TagLib/AudioFile+TagLibLoading.swift) · [Adapter outcomes (line 21)](../../AudioMator/Infrastructure/TagLib/TagLibAudioMetadataPipeline.swift) · [Reservation (line 24)](../../AudioMator/Domain/MetadataEditing/FileMutationCoordinator.swift) · [Commit and readback (line 40)](../../AudioMator/Features/Main/Application/MetadataFileMutationExecutor.swift)

The common executor owns path-level serialization, while each feature establishes what its expected state means. Inspector and raw conflict-resolution routes carry and compare baselines. Captured provider plans carry a reviewed fingerprint. Lyrics reconstruct authority from the newest model by UUID. Rename combines an in-process move transaction with a distinct post-move readback and publication path. The exchange planner previews captures while execution independently interprets them as draft setters and patch components. AM-01, AM-03, and AM-05 demonstrate why a revision token alone cannot guarantee fidelity. An operation needs a coherent target identity, reviewed snapshot or revision, and typed intent. Every commit route should either carry that context intact or explicitly request a new review. The write plan is the natural shared boundary, while reservation remains the lowest-level app transaction mechanism.

The central state model has useful generation counters, watched-folder mutation epochs, a persistent refresh-required set, and batched publication. It nevertheless couples source caches, security grants, monitoring, draft reconstruction, save progress, and operation completion in one MainActor object and its workflow extensions. The consequence is visible in AM-06 and AM-14. Correctly applying a disk observation to a durable file identity is separate from deciding whether the active draft can be recreated. UI sessions should own their draft lifecycle and apply completion should identify the session it is allowed to update. File collections and disk identity should reconcile whether or not the source is currently visible. A smaller ownership change at those boundaries is preferable to a broad state rewrite.

Batch writes intentionally permit partial results at file boundaries and report started commits even after cancellation. This is suitable for independently authored media files. Rename’s staging contract has a different recovery problem because several moves jointly establish a consistent name set. A delayed synchronous commit may also keep a reservation while the storage operation is pending. Abandoning a commit via timeout could misreport its outcome, so define operational recovery and telemetry expectations around that boundary before imposing a blanket timeout. Content capabilities, native layouts such as ID3v2.3 independent dates, and best-effort erase also warrant explicit constraints rather than silent fallbacks. ## Design decisions and uncertainties

- **Raw editing and destructive operations.** Raw metadata intentionally has a lower-level contract than semantic writes, and erase-all is best effort for container-native structures. These are legitimate feature boundaries. A raw preview must still correspond to actual array edits. An intentional clear is distinct from the unintended sibling loss in AM-01.
- **File freshness.** Stable IDs per path, separate metadata/file revisions, conservative capability checks, narrower automatic refresh on activation, and explicit folder-monitor resource limits have defensible purposes. Stable IDs should survive refresh for UX continuity. A reviewed write needs stronger provenance. The selected-file activation refresh and monitor cap each leave observable staleness scenarios, and monitoring status should convey them.
- **Renumbering and close behavior require a product decision.** Clarify whether a start of zero clears the first track number or should store a supported zero value, and where zero padding is expected to persist. Clarify whether Auto Apply should cancel on close or become an app-owned background operation. The affected implementations can be made internally consistent under either policy.
- **Artwork target drift remains a potential issue.** Download completion resolves surviving captured IDs and the multi-file function mutates the current draft. The artwork sheet constrains ordinary same-window selection changes. The exact remaining interactive paths and the severity of watch-driven selection drift were not reproduced. Scope a future model test to a changed selection or source while a download is pending. [Download handoff (line 164)](../../AudioMator/Features/Main/ViewModels/AudioViewModel+ArtworkLookup.swift) · [Multi-file draft action (line 260)](../../AudioMator/Features/Main/ViewModels/AudioViewModel+Import.swift)
- **Privacy boundaries.** The WebKit policy uses HTTPS navigation restrictions and nonpersistent storage. The documented reach of WebKit subresources and Apple-returned artwork URLs is wider. This audit established a premature provider query and disclosure omissions. It did not establish an exploit through these host policies. The GitHub update path manually checks version and opens release information. No installation mechanism was observed. [Embedded browser policy (line 1)](../../AudioMator/Features/OnlineMetadataBrowser/Views/EmbeddedWebView.swift) · [Update handoff (line 38)](../../AudioMator/Infrastructure/Updates/UpdateCheckPresenter.swift) · [Artwork and WebKit disclosure (line 123)](../ACKNOWLEDGEMENTS_AND_PRIVACY.md)

- **Severity sensitivity.** Independent reviewers agreed on the reachable code paths for LRCLIB stale results and interrupted rename. They differed on impact weighting. The ratings above treat a potentially wrong-target write and a stranded batch without built-in recovery as high because of their consequences. The lyrics case requires the app to observe the intervening change, and the interruption experiment preserved the original audio bytes. Neither event frequency was measured.

## Prioritized recommendations

1. **Gate the next release on import correctness.** First repair AM-01 and AM-02. Add tests that exercise the actual write-entry execution path and assert the exact field set, unaffected siblings, correct target identity, and disk readback. Use constant external CSV/TXT fixtures as well as exporter-generated cases.
2. **Protect revision provenance and interrupted file moves.** Resolve AM-03 to AM-05 before relying on these workflows over existing libraries. Require a coherent baseline after moves, reject stale provider results, and make staged rename recovery reconstructible after restart. Test a competing disk change, genuine reload failure, and process interruption independently.
3. **Unify session and completion handling.** Address AM-06 and AM-08 together with the applicable close/dirty-draft decision. Add specific regression tests for reopening dirty editors, rescan-driven pruning, concurrent edits during a save, and cancellation before a subsequent commit. Keep the real outcomes of begun commits.
4. **Align user promises and operational recovery.** Resolve MusicBrainz request timing and LRCLIB disclosure, then repair the watcher, cache, and storefront issues. Make raw and renumber previews reflect exact commit inputs. Review large-library import and planner performance using the measured workload classes.
5. **Raise the quality of release evidence.** Fix the local helper’s exit and input handling, retain the fail-closed named gate, run key filesystem and metadata cases on signed builds and supported OS versions, and establish a clean path toward Swift 6 isolation checks.
